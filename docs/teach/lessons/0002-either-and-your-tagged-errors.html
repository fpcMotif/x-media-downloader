Lesson 2 · Monadic design in your codebase

Either & your tagged errors

From Lesson 1: Option answers “is anything there?”. This lesson is the other half of your refactor — Phases 0–3 — which answer “it failed, and here is exactly why.”

The one idea. Either<E, A> is Option with the absence labelled: the same monad, now carrying a typed reason on the failure track. Your Data.TaggedError classes are that E. Effect’s Effect<A, E, R> is the same machine with an error channel — so “typed errors” is just doing to failure what Option did to absence: putting it in the type so it composes and the compiler can’t let you ignore it.

1 · Either = Option that remembers why

Recall Option<T> = Some T | None. Now attach data to the empty case:

Either<E, A> = Left<E> | Right<A>  and  Option<T> ≅ Either<unit, T>  (None = a Left carrying no information)

It is right-biased: map/flatMap act on the Right (success); a Left short-circuits the rest untouched.2 That is precisely the railway from Lesson 1 — but now the failure track carries a payload. Everything you learned about Kl(Option) transfers verbatim to Kl(Either E): arrows are A → Either<E, B>, composition is flatMap, the identity is Either.right, and the monad laws still hold.

2 · Your tagged errors are the E

Data.TaggedError builds the error type — a class with a _tag discriminant and typed fields:1

export class OAuthError extends Data.TaggedError('OAuthError')<{
  readonly message: string
  readonly context?: 'state-mismatch' | 'no-code' | /* … */
}> {}

When several can occur, the error type is their discriminated union — a sum type of failures:

OAuthError | Aria2RpcError | OffscreenSaveError | ConvexHttpError | …

That union is the whole reason catchTag works: it matches on _tag and the compiler narrows the remaining union; handle them all and E becomes never (provably exhaustive).1 The _tag isn’t decoration — it’s the discriminant that lets the type system tell your failures apart.

A note on your current code

Today your classifyUploadError matches errors by regex on the message string. That worked, but it’s the pre-typed-error pattern: stringly-typed dispatch. Now that the failures are a tagged union, the idiomatic next step is to switch that to catchTag/match on _tag — turning a fragile string match into an exhaustive, compiler-checked one. (Your Phase 2 work deliberately kept the message stable precisely so that classifier wouldn’t break — a good bridge, and a natural thing to retire later.)

3 · Either is a bifunctor

Right-biased map transforms the success. To transform the error — say, wrap a low-level failure as a domain one — use mapLeft (or bimap for both at once).2 You did this by hand in Phase 4: Effect.tryPromise({ try, catch }) where the catch maps the thrown cause into new DownloadError({ reason: errorReason(cause) }) — that’s a mapLeft over the error channel. Each side obeys the functor laws independently.

2 · Effect generalises all of this

Effect<A, E, R> is the same monad with three slots: A success, E the error channel (the Either Left — your tagged errors), R the requirements.1 Errors accumulate as a union in E automatically as you compose. Your DownloadStrategy is exactly a Kleisli arrow over this monad:

save: (req: SaveRequest) => Effect<DownloadHandle, DownloadError>

Same fish, bigger pond: flatMap still composes the steps, a failure still short-circuits, and now the set of possible failures is written in the type for the caller to see.

The line that matters: failure vs defect

Effect splits errors in two,4 and this is the rigorous form of Lesson 1’s “don’t reinvent exceptions”:

Effect.fail — failureEffect.die — defect
Whatexpected, domain, recoverablebug / invariant violation, unrecoverable
In E?yes (typed)no (E = never, terminates)
Analogychecked exceptionunchecked exception

This is the boundary you navigated in the refactor. You converted the escaping domain throws — OAuth consent, aria2 RPC errors — into tagged failures, because a caller can sensibly react to them. You left the invariant/boundary throws inside runUpload’s try/catch alone. The theory says exactly that: model recoverable domain outcomes as typed failures; let genuine defects stay defects. Putting everything in E would be reinventing exceptions with extra ceremony — the over-application Wlaschin warns against.5
