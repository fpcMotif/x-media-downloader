Lesson 1 · Monadic design in your codebase

The monad behind your refactor

Mission: reason about & defend the Option / tagged-error patterns you just shipped — from category theory, and against the null + throw alternative.

The one idea. A monad is the structure that lets you compose functions whose results are “embellished” — wrapped in Option, in an error, in an effect.1 Your Phase 4 refactor took functions that were secretly partial (… | null) and moved them into a category where they compose lawfully. That single move is also the entire justification for it.

1 · Your code already lives in a category

A category is just: objects, arrows between them, a way to compose arrows, an identity arrow, and two laws (composition is associative; identity does nothing).2 In programming the objects are types and the arrows are functions A → B. Ordinary functions compose perfectly: g ∘ f.

The trouble starts with partial functions. Before the refactor:

tweetIdOfArticle: Element → (string | null)
findArticle:      (ParentNode, string) → (Element | null)

These don’t compose. You can’t feed a string | null into something expecting a string — you have to stop and hand-write a === null check at every seam. The null is data with no structure attached, so the burden of threading it is on you, every time (and the day you forget is the runtime crash).3

2 · Option is a functor, then a monad

Functor. Option maps every type T to Option<T> (= Some T | None, the sum type T + 1) and every function via Option.map. It obeys the functor laws (map(id)=id, map(g∘f)=map(g)∘map(f)) — which is what makes map safe to reason about.

Monad. A functor becomes a monad with two operations1 — and you are already calling both:

Category theoryWhat it doesIn your Effect code
unit · η : A → T Awrap a plain valueOption.some(x)
multiplication · μ : T(T A) → T Aflatten one layerOption.flatten
bind (= η + μ)compose a step that may be absentOption.flatMap

The structure must satisfy the monad laws — left identity, right identity, associativity:

flatMap(some(a), f) = f(a)  ·  flatMap(m, some) = m  ·  flatMap(flatMap(m,f),g) = flatMap(m, x => flatMap(f(x),g))

3 · The Kleisli category — where your refactored functions live

Take any monad T and build a new category Kl(T): same objects (types), but an arrow A → B is now a function A → T B.4 These are Kleisli arrows. Every function you converted in Phase 4 is one:

convexOriginPattern: string → Option<string>
aria2OriginPattern:  string → Option<string>
pickVideoVariant:    Variant[] → Option<Variant>
tweetIdOfArticle:    Element → Option<string>
findArticle:         (ParentNode, string) → Option<Element>

In Kl(Option) the composition of two Kleisli arrows is the “fish” f >=> g, implemented exactly as a => flatMap(f(a), g) (nLab: μ ∘ T(g) ∘ f), and the identity arrow is Option.some.4 You saw this inside findArticle, which composes over tweetIdOfArticle with Option.isSome(id) && id.value === tweetId.

The punchline. The monad laws are the category laws (associativity + identity) for Kl(T). Milewski: “a monad is just a funny way of composing embellished functions so that they form a category.”1 So “move partial functions into Option” literally means “give them a lawful composition they didn’t have as … | null.” And your tagged errors are the same story in Kl(Either): an arrow A → Either<E, B>, where Maybe<T> ≅ Either<unit, T>.

2 · The case against null + throw

Because the structure is lawful, every practical win below follows from it — this is your justification, point by point:

PropertyT | null + throwOption / Either (monad)
Absence/failure visible in the typeNo — throw is an invisible second exit; null is easy to ignore3Yes — the compiler forces you to handle None/Left
Composition of failing stepsManual === null at every seamAutomatic short-circuit via flatMap (railway)5
Honest signaturesstring → string that secretly returns null liesstring → Option<string> declares the partiality
Safe refactoringReordering null-checks is error-proneMonad laws ⇒ inline / reassociate flatMaps freely
Set of failures is knowableAny exception, anywhereEnumerated in the type (Data.TaggedError union)

This is the same lesson the industry keeps relearning: Tony Hoare calls inventing null his “billion-dollar mistake,” and notes he already knew in 1965 that disjoint unions (sum types — exactly Option) were the right answer.3

The caveat — which is exactly what you did

Wlaschin, who popularised the railway model, also wrote a follow-up: only use it for domain problems; don’t reinvent exceptions; don’t thread Either through everything.5 Your Phase 4 curation — declining the adapters/x resolve chain because converting it produced .value! and getOrElse(() => null) round-trips at the Preact boundary — is that wisdom applied. The theory says when Kleisli composition pays: when arrows actually chain. Where they don’t, the wrapping is cost without composition. You read that correctly.
