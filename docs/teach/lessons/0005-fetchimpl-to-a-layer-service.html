Lesson 5 · Apply it

From hand-threaded fetchImpl to a Layer service

Mission: master the thinking, not the migration. This takes Lesson 4’s R/Reader channel from idea to a runnable change on your own fetchImpl dependency — and, just as importantly, when not to do it.

Spaced recall (no peeking). Two from earlier lessons: (i) what classic monad is the R channel, and what must R equal before an effect can run? (ii) what does flatMap short-circuit on? Check the glossary after.
The one idea. Passing a dependency as a parameter — your cfg.fetchImpl — is the Reader monad threaded by hand. The R channel is the same idea with the compiler doing the threading: the need is recorded in the type, and you swap the implementation (real ⟷ stub) by swapping a Layer. “Dependency injection” is just the Reader monad rediscovered.1

1 · Before — Reader by hand (your real code)

Today the fetch dependency is threaded through plain cfg/deps objects:

// makeAria2RpcPort(cfg: { rpcUrl; secret; fetchImpl: typeof fetch })
const doFetch = bindFetch(cfg.fetchImpl)
// DriveDeps { fetchImpl: typeof fetch; fetchSource; … }

This works, but the dependency is invisible in the result type, and every caller must drill fetchImpl down by hand. You are personally playing the part of the Reader monad’s ask. (You’ve already done the typed version once — SettingsService — so you know the shape.)

2 · The migration — three moves

Mirror your settings module. (Full runnable version: src/core/teach/fetch-service.demo.test.ts.)

// (1) NAME the dependency as a service
class FetchService extends Context.Service<FetchService,
  { readonly fetch: (url: string) => Effect.Effect<Response> }
>()('teach/FetchService') {}

// (2) BUILD a Layer (the recipe) — real impl
const FetchServiceLive = Layer.succeed(FetchService, {
  fetch: (url) => Effect.promise(() => fetch(url)),
})

// (3) WRITE programs against the service — the need shows up in R
const statusOf = (url: string): Effect.Effect<number, never, FetchService> =>
  Effect.gen(function* () {
    const http = yield* FetchService            // <- the Reader's "ask"
    const res = yield* http.fetch(url)
    return res.status
  })

statusOf never names fetch. Its type says R = FetchService, so it cannot run until you provide one — the compiler enforces it.

3 · The payoff (run it)

Swap the Layer to stub the network — zero real fetches in tests

const stub = (status: number) => Layer.succeed(FetchService,
  { fetch: () => Effect.succeed(new Response(null, { status })) })

await Effect.runPromise(Effect.provide(statusOf(url), stub(204)))  // => 204

bunx vitest run src/core/teach/fetch-service.demo.test.ts → 3 passed

Same program, swap stub(500) → stub(200) and the result changes. In production you provide(…, FetchServiceLive) at the edge. The dependency is now tracked, swappable, and un-drillable — and you never touched the network in a test. Try editing a stub status and re-running.

4 · The categorical thread

The Reader monad is just “a value that depends on an environment”: Reader<R, A> ≈ (R) => A. Then:

yield* FetchService = Reader’s ask (read the env)  ·  Effect.provide = apply the environment (turn R → A into A)  ·  R1 | R2 = needs both (a product of environments)

So this lesson isn’t a new trick — it’s the same monad machinery from Lessons 1–4 applied to dependencies. flatMap still composes; it now also threads R inward until provide discharges it.

5 · The judgment — when to migrate, when not (defend it)

Keep it a plain parameter when…Promote to R + Layer when…
one leaf util, one caller (your aria2 port in isolation)cross-cutting dep used in many places (fetch, clock, logger, config)
no need to stub it in testsyou want to swap real ⟷ stub without prop-drilling
the wiring is trivial and localthe dependency graph is deep (Layers compose it for you)

This is the same restraint from Lessons 1–2 (don’t over-apply). fetchImpl is a strong candidate — it’s everywhere and you stub it constantly. SettingsService you already promoted (good call). A one-off cfg field used by a single port? Often fine as-is. Mastery is knowing which, and being able to say why.
