Lesson 3 · Make it stick

The laws, as tests you can run

Lessons 1–2 told you the functor & monad laws hold. This lesson makes you feel them: a runnable test, already in your repo, that checks each law over hundreds of random inputs — and a sabotage exercise that proves it has teeth.

The one idea. A law you only read is a belief. A law written as a property test is knowledge the machine re-verifies on every run. Property-based testing1 flips unit testing around: instead of one example (expect(f(2)).toBe(3)), you state what must hold for all inputs and let fast-check hunt for a counterexample — then shrink it to the smallest failing case.2

It’s already wired up

I added a runnable file to your repo (delete it any time — it’s a teaching artifact):

src/core/teach/option-laws.test.ts

Open it next to this lesson. It contains 8 properties: the two functor laws, the three monad laws, and three checks that your own functions (convexOriginPattern, aria2OriginPattern, pickVideoVariant) behave as lawful Kleisli arrows.

The laws, in code

Each law is one fc.property. The pattern is always: generate inputs → assert the two sides are equal. eqOption is just “both None, or both Some of the same value.”

// functor identity:  map(m, x => x) === m
fc.assert(fc.property(anyOption, (m) => eqOption(Option.map(m, (x) => x), m)))

// monad left identity:  flatMap(some(a), f) === f(a)
fc.assert(fc.property(fc.string(), (a) => eqOption(Option.flatMap(Option.some(a), f), f(a))))

// monad associativity:  flatMap(flatMap(m,f),g) === flatMap(m, x => flatMap(f(x),g))
fc.assert(fc.property(genSomeString, (m) =>
  eqOption(Option.flatMap(Option.flatMap(m, f), g),
           Option.flatMap(m, (x) => Option.flatMap(f(x), g)))))

And your real arrow, proven to plug into the law correctly:

// convexOriginPattern obeys left identity
fc.assert(fc.property(fc.webUrl(), (u) =>
  eqOption(Option.flatMap(Option.some(u), convexOriginPattern), convexOriginPattern(u))))

Do the loop (this is the lesson)

1 · Run it — see green

bunx vitest run src/core/teach/option-laws.test.ts

Expect Tests 8 passed (8). Each line just ran ~100 random inputs and held.

2 · Sabotage a function — watch the property catch it

In src/core/resolver/index.ts, temporarily make pickVideoVariant pick the first mp4 instead of the max-bitrate one:

// return Option.some(mp4.reduce((best, v) => ((v.bitrate ?? 0) > (best.bitrate ?? 0) ? v : best)))
return Option.some(mp4[0])   // <-- deliberately wrong

Re-run. fast-check fails fast and shrinks to a minimal counterexample — typically two mp4 variants where the second has the higher bitrate:

Property failed after 2 tests … counterexample: [[{mp4,bitrate:0},{mp4,bitrate:1}]]

That tiny case is the proof your “highest-bitrate” invariant is real and the test guards it. Now revert the change and watch it go green again.

3 · Generate your own property (the part that sticks)

Writing a property forces you to articulate an invariant — that’s the retrieval+generation effort that builds long-term memory.3 Add one for aria2OriginPattern:

“For any URL, the result — when present — contains no port number.”

it('aria2OriginPattern drops the port', () => {
  fc.assert(fc.property(fc.webUrl(), (u) => {
    const p = aria2OriginPattern(u)
    return Option.isNone(p) || !/:\d+/.test(p.value.replace(/^https?:/, ''))
  }))
})

Run it. Then bring it to me — I’ll tell you if the property is actually saying what you think (a classic trap: a property that’s true but vacuous).

Why this builds storage strength, not just fluency. Re-reading the laws feels like learning but fades. Running them, breaking them, and generating new ones is “desirable difficulty” — effortful retrieval that durably encodes the idea.3 Next session I’ll space this: I’ll ask you to state the associativity law from memory before we build on it.
