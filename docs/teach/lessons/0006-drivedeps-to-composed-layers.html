DriveDeps → composed Layers

Mission: master the thinking. Lesson 5 migrated one dependency; this decomposes a real bag of them — and shows the dependency graph for what it categorically is: arrow composition.

Spaced recall (no peeking). From Lessons 4–5: (i) in Layer<ROut, E, RIn>, which slot is the requirements? (ii) what must an effect’s R be before it can run? (iii) what does provide do to R? Then check the glossary.
The one idea. DriveDeps is a god-bag mixing three different concerns: capabilities (fetchImpl, fetchSource), config (accessToken, rootFolderId), and mutable state (folderCache: Map). The migration is: give each concern its own service, model the cache as a Ref (effectful State), and let Layers build & wire them — including a layer that depends on other layers. Provide the whole graph once, at the edge.

1 · Before — one bag, three concerns

export interface DriveDeps {
  readonly accessToken: string                       // config
  readonly rootFolderId: string                      // config
  readonly fetchImpl: typeof fetch                   // capability
  readonly fetchSource: (url: string) => Promise<Response>  // capability (SSRF-guarded)
  readonly folderCache: Map<string, string>          // mutable state
}

Everything is threaded by hand and invisible in result types. Mixing config + capabilities + state in one parameter is the smell; each wants a different home.

3 · Effectful state: the cache becomes a Ref

A Ref<A> is a mutable reference to an immutable value with atomic get/update — the effectful cousin of the State monad.2 Create it inside Layer.effect, keep it private, expose methods:

const FolderCacheLive = Layer.effect(FolderCache, Effect.gen(function* () {
  const ref = yield* Ref.make<Record<string, string>>({})           // created ONCE
  return {
    get: (h) => Ref.get(ref).pipe(Effect.map((rec) => Option.fromUndefinedOr(rec[h]))),
    set: (h, id) => Ref.update(ref, (rec) => ({ ...rec, [h]: id })),
  }
}))

Because layers are memoized by reference, this Ref is allocated once and shared by everyone who needs FolderCache — a single source of truth, no global mutable variable.3 (Note: fromUndefinedOr, not fromNullable — the latter doesn’t exist in your beta.92.)

4 · Layers depending on Layers

Layer<ROut, E, RIn>: produces ROut, requires RIn.1 The uploader needs all three, so its type carries them — and you discharge them by providing the composed dependency layer:

const DriveUploaderLive: Layer<DriveUploader, never, FetchService | DriveConfig | FolderCache> =
  Layer.effect(DriveUploader, Effect.gen(function* () {
    const http  = yield* FetchService           // requirements resolved at CONSTRUCTION,
    const cfg   = yield* DriveConfig            // so the service's own methods have R = never
    const cache = yield* FolderCache
    /* … ensureFolder uses cache then http; upload uses ensureFolder then http … */
  }))

const appLayer = DriveUploaderLive.pipe(
  Layer.provide(Layer.mergeAll(FetchServiceLive, DriveConfigLive, FolderCacheLive)),
)   //  provide = feed outputs into requirements;  merge = put them side-by-side

5 · The payoff (run it)

The cache dedupes folder creation — provably, with the network stubbed

bunx vitest run src/core/teach/drive-layers.demo.test.ts → 1 passed

The demo uploads twice for alice and once for bob through a stub FetchService that counts calls. Result: 3 uploads, but only 2 folder-creations — the second alice upload hits the Ref cache. Swap FetchServiceLive for a stub and the whole graph runs offline. That is the entire value: testable, swappable, shared-by-construction.

6 · The categorical thread — the graph is composition

A Layer<ROut, E, RIn> is a morphism RIn → ROut in a category of resource-recipes. Layer.provide is composition ∘; Layer.merge is a product; memoization is sharing of a sub-object.

So the dependency graph you wired is literally arrow composition — the same structure from Lesson 1, lifted to services. The environment R = A | B | C is a product (“needs all of them”), and provide reduces it toward never exactly as Kleisli composition reduces a chain. Nothing new under the sun — just the monad/category toolkit pointed at dependencies.

7 · The judgment — is this migration worth it? (defend it)

Often, for one adapter: partly. Splitting DriveDeps into four services + four layers is ceremony if nothing else consumes them. The win appears when capabilities are shared:

  • Extract & share: FetchService (and a clock/logger) — used by drive, dropbox, aria2, convex. Define once, provide once, stub everywhere. Strong yes.
  • Keep as state-service: FolderCache — genuinely stateful and worth a Ref service if shared or tested.
  • Maybe leave: accessToken/rootFolderId are per-upload runtime values; a plain argument or a small DriveConfig is fine — don’t Layer-ify a string just because you can.

Mastery is making this call per concern, not per habit — the same restraint as declining the Option resolve-chain in Phase 4.
