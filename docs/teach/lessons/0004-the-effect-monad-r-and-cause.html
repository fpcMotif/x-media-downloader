The Effect monad: R & Cause

You met the pieces: Option (absence), Either (typed failure), and the laws that make them compose. Effect fuses them — and adds a third channel you’re already using.

The one idea. Effect<A, E, R> is approximately R → Promise<Either<E, A>>, kept lazy.3 It bundles three classic monads into one value: Reader (the R requirements), Either (the E failures — Lesson 2), and Task/Async (the A deferred success). Everything from Lessons 1–3 still holds: it’s just a very rich monad, and flatMap is still Kleisli composition — now threading all three channels at once.

1 · The R channel is the Reader monad — and you use it

The third slot is requirements: the services an effect needs before it can run.1 Your settings module is a textbook example:

// src/core/settings/index.ts
export class SettingsService extends Context.Service<SettingsService>()(/* … */) { /* get: Effect<Settings> */ }
export const SettingsServiceLive = Layer.succeed(SettingsService, { /* impl */ })

// a program that READS settings has R = SettingsService:
const getViaService: Effect.Effect<Settings, never, SettingsService> = /* … */
// you can WRITE it before any implementation exists. To run, you PROVIDE one:
Effect.runPromise(Effect.provide(getViaService, SettingsServiceLive))   // R: SettingsService → never
  • Context = a type-safe map Tag → Service — the DI container the R reads from.1
  • Layer = a composable recipe to build a service (your SettingsServiceLive).
  • provide discharges a requirement, shrinking R toward never; an effect can only run once R = never.
  • Subtlety: read R1 | R2 as “needs both R1 and R2”, not “either.”1

Categorically this is the Reader (a.k.a. environment) monad: a computation that is secretly a function from an environment R. Note you also do DI the manual way elsewhere — DriveDeps, the cfg objects passed to makeConvexHttpPort/makeAria2RpcPort. Same idea, untyped-in-the-result: the R channel is the version the compiler tracks and composes for you. Your DownloadStrategy.save has R = never (self-contained) — that’s why it just runs.

2 · Cause & Exit — where “lossless” becomes literal

Running an effect yields an Exit = Success(A) | Failure(Cause<E>) — you already destructure this with Effect.runPromiseExit + Exit.isFailure in your aria2/strategy tests.

Cause<E> is the full story of failure, not just a message.2 Its leaves are exactly Lesson 2’s distinction, plus interruption:

LeafMeaningIn your world
Fail<E>expected, typed failureyour DownloadError, OAuthError, …
Diedefect (unexpected bug)the invariant throws you left in runUpload
Interruptfiber was cancelleda cancelled download/sweep

And the clever part: these leaves combine through Sequential and Parallel operators — a semiring over E.2 That is what makes the model lossless: if two parallel uploads fail, Cause keeps both; if a finalizer dies while the body already failed, it keeps both, in order. A bare throw can carry exactly one error and forgets the rest.

3 · Why fuse three monads instead of stacking them?

In Haskell you could stack ReaderT R (ExceptT E IO). But transformer order matters — StateT s (ExceptT e m) and ExceptT e (StateT s m) mean different things — and the nesting is awkward.3 Effect bakes the combined stack into one type, so you get Reader + Either + Async with no ordering pitfalls, all three concerns visible in the signature, and one flatMap that:

threads R inward · short-circuits on E (the railway) · sequences the async A — while still obeying the monad laws you tested in Lesson 3.

So the whole arc closes: Option and Either are the small monads; Effect is the big one your app runs on; the laws and Kleisli composition are the same throughout. You now have the full vocabulary to read — and defend — every signature in your refactor.
