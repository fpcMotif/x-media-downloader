/improve-codebase-architecture round 3 branch: test/cloud-coverage-100

Deepening opportunities

Two prior rounds refuted 11/11 candidates — the pure cores under src/core/** are deep and held at 100%. This round looks where the friction actually lives now: the effectful shells in src/background/**. Three of them — cloud-upload, sync-outbox, tab-broadcaster — are deep modules whose seam is in the wrong place: they construct their own side-effects (storage items, browser.* ports, the upload runtime), so the behaviour they own can't be exercised through their interface. Their tested siblings (daily-budget-store, admission-gate, saved-status) all inject those seams.

src/core/**
pure reducers · 100% gate · deep & tested
src/background/**
10 shells · 7 inject seams & are tested · 3 don't
src/entrypoints/**
background.ts (1298) + overlay (1662) · excluded by design

The shape of the friction — depth is fine, the seam is misplaced

A deep module is a lot of behaviour behind a small interface. These shells are deep — makeCloudUpload exposes 11 methods over 563 lines. The problem isn't shallowness. It's that the interface is supposed to be the test surface, and here you can't cross it: the storage item, the browser.* calls, and the provider runtime are built inside the factory, so a test has nothing to substitute. The deep behaviour is sealed behind glue the test can't reach.

The fix is not "add tests" — it's a seam relocation: move side-effect construction out to injected ports (the proven makeDailyBudgetStore(deps) pattern). The interface barely changes; the depth stays; the seam moves to where callers and tests already stand.

Candidate ①

Relocate the Cloud Upload seam

Strong · top recommendation
src/background/cloud-upload.ts 563 LOC · 0 tests ↳ reuses core/cloud/upload-job.ts tested model: src/background/daily-budget-store.ts

Problem

The pure Upload-Job ledger (enqueue / claim / recordSuccess / recordFailure / readyJobs / capLedger) is fully tested in core/cloud/upload-job.ts. But the orchestration that drives it — drainUploadJobs (lines 303–375) — owns the bugs that actually bite: the claim→persist-lease→upload→record→cap→mirror ordering, the provider-disconnected-mid-flight branch (319–327), and the re-kick vs. arm-backoff-alarm decision (366–374). None of it is reachable: makeCloudUpload calls storage.defineItem() (163), ManagedRuntime.make() (172), and browser.alarms/action/identity inline. The deps interface injects only getSettings, fetchImpl, queueError, getBackfillRecords — the four that don't matter for the drain.

Solution

Move side-effect construction into CloudUploadDeps, exactly as makeDailyBudgetStore({ storage, now }) already does:

  • ledger: LedgerStore — get()/set() over the wxt item
  • upload: UploadPort — drive/dropbox/resolveDriveRoot (wraps the runtime)
  • alarms / badge — the two browser.* sinks
  • setSettings — passed in, not imported
  • authFlow — the one genuinely-browser-bound seam (OAuth), isolated

The CloudUpload interface (11 methods) is unchanged. The entrypoint wires the live ports; tests wire fakes and drive drainUploadJobs through real ledger transitions.

BEFORE — 5 side-effects sealed inside, 1 drain untestable
AFTER — ports injected, drain exercised through the interface
Leverage

One injected UploadPort pays back across the live drain, boot-resume, alarm-wake, retry, and backfill — five call sites, one fake.

Locality

The lease-ordering invariant (persist 'uploading' before the slow upload) becomes a test, not a load-bearing comment on line 334.

Deletion test

Earns its keep. Delete the drain and its logic reappears inline in background.ts. The friction is purely where the seam sits.

Candidate ②

Inject the Sync Outbox drain seam

Worth exploring
src/background/sync-outbox.ts 168 LOC · 0 tests ↳ core/sync/outbox.ts tested

Problem

Same anti-pattern, smaller surface. makeSyncOutbox({ queueError, fetchImpl }) creates outboxItem and syncStatusItem internally (lines 43, 60) and calls browser.permissions.contains inline (120). So drainOutbox (72–106) — the FIFO loop with the first-failure-stops-and-marks-backoff rule, and runSyncConnectionTest's four-stage precondition ladder (URL → secret → valid origin → permission) — can't be driven by a test. The pure outbox reducer is tested; the loop that calls it isn't.

Solution

Inject the two storage items (as one OutboxStore) and the permission probe. Because this is the second durable-FIFO-drain shell next to cloud-upload, the seam shape is now real — design the injected store/port once and let both shells satisfy it. (Two adapters earn the seam; one would not.)

Caution: don't over-reach into a shared "Drainer" module. A prior round established the drains share the SerialQueue (already extracted) but little else — upload has per-job leases, outbox has whole-batch backoff. Share the dependency shape, not the loop body.

Two adapters, one seam shape
interface DurableDrainDeps {
  store:  { get(): Promise<T>; set(v:T): Promise<void> }
  status: { set(s): Promise<void> }
  // upload adds:  alarms, badge, upload
  // outbox adds:  permission probe
}
makeSyncOutbox(deps)  ── drainOutbox    ✓ testable
makeCloudUpload(deps) ── drainUploadJobs ✓ testable

The shared shape is the seam. The loop bodies stay distinct — leverage without a false abstraction.

Tests improve

The "stop at first failure, record backoff, surface to popup" path becomes a 6-line unit test instead of a manual sync-against-a-live-deployment.

Locality

The precondition ladder (URL/secret/origin/permission) gets one home with one verdict per branch.

Deletion test

Earns its keep — the drain is the only thing standing between a download and a stuck silent outbox.

Candidate ③

Lift the clear-tab ordering decision into the core

Worth exploring
src/background/tab-broadcaster.ts 121 LOC · 0 tests → core/clear/ (new pure fn)

Problem

sendClearToTabs (78–112) carries a real, safety-critical decision tangled inside an I/O loop: try the originating tab first, stop at the first tab that actually has the article mounted, and distinguish "mounted but the flip failed" from "not mounted anywhere" (an empty results array). That ordering is the guarantee that a background Bookmarks/Likes tab can't win the broadcast and un-bookmark a post the user only meant to drop from its feed — a genuine data-loss guard. Yet makeTabBroadcaster() takes no deps and calls browser.tabs.* inline, so the guard has zero tests.

Solution

Separate the decision from the I/O. Extract a pure orderTabsForClear(ids, preferTabId) (and the interpretClearResults(per-tab responses) verdict) into core/clear/, where it's trivially table-tested. The broadcaster keeps only the thin for…sendMessage walk. Alternatively, inject a tabs port — but the ordering rule is the part with the bug surface, so lifting it is the higher-leverage move.

New domain term for CONTEXT.md: Clear Target Order — the origin-tab-first precedence that decides which tab gets to perform a verified flip.

The decision joins core/clear next to decideSettle, pageScope, worklist — same seam, same test idiom.

Candidate ④

Give runUpload its own seam & tests

Worth exploring
src/core/cloud/http.ts 100 LOC · 0 direct tests in the 100% gate — only e2e-covered

Problem

http.ts holds the provider-agnostic upload template method — the simple-vs-streamed size dispatch, the error→UploadOutcome mapping, and CloudHttpError. It's the shared skeleton both Drive and Dropbox call, and it sits inside the 100% coverage gate — but it has no co-located test. It's reached only transitively through upload-pipeline.e2e.test.ts, so its branches (a 413, a half-stream abort, a sourceGone) are covered by accident, not by intent. This is the most likely true source of the red gate the branch is chasing.

Solution

Add http.test.ts that drives runUpload directly with a fake byte sink and synthetic responses, asserting one verdict per error class. This is a characterisation step, not a reshape — the module is already deep and well-placed; it's just missing its own test surface. (Also fold the redundant cloud-services.ts pass-through — three Layers and a mechanical test — into its one caller while you're here.)

Coverage reached by intent vs. by accident
Tests improve

Error-class branches become explicit assertions, so a regression in size-dispatch fails a fast unit test, not a slow flaky e2e.

Smallest lift

No interface change at all — pure test addition. Likely closes the actual red-gate gap on this branch.

Deletion test

Earns its keep — delete runUpload and the dispatch duplicates into both uploaders.

Candidate ⑤

The in-flight Transfer Registry

Speculative · previously refuted
src/entrypoints/background.ts 7 module-level Maps + timer wheel excluded from the coverage gate by design
⚠ Honesty flag. A prior round refuted a "hand-off machine" extraction here, and the standing conclusion was "the codebase is already deep; the residual gaps are tests, not modules." I'm surfacing this anyway because it is the single largest untested surface in the repo — but with the reframing below, and a clear-eyed view of why it may re-lose.

Problem

Every pure decision is extracted and tested — decideTerminalOutcome, planInterruptRetry, planBootReconcile, classifyTransfer. But the state they thread through has no owner: requestIdByDownloadId, requestMetaById, interruptAttemptById, pendingRetries, retryTimeouts, inFlight, clearOriginTab — seven Maps plus a timer wheel — are mutated across ten functions (settleBrowserDownload, fireInterruptRetry, scheduleInterruptRetry, reconcileTransfersOnBoot, reconcileStuckDownloads, handleDownload, onDownloadChanged). The three-ledger tie-break and the "flush transfers before durable writes" ordering are load-bearing comments, not invariants.

Reframe (vs. the refuted version)

The earlier proposal tried to extract a state machine — and lost, because the decisions were already pure and a machine just added a layer. This reframe owns only the correlation state: a TransferRegistry module holding the seven Maps + an injected Clock/timer port, exposing start / onDelta / onRetryFire / reconcile / reset. The pure planners stay where they are; the registry just gives their inputs and effects a single tested home.

Seven Maps, no owner

Four of ten writers shown. No seam → no test for the wiring where the real recycle-race bugs live.

Why it might re-lose

The state is genuinely fused to the chrome.downloads timer lifecycle; a registry may relocate the entanglement rather than dissolve it.

Why it might be worth it

It's the one untested surface where the docs themselves flag recycle races and dual-ledger tie-breaks as fragile.

Deletion test

Concentrates — the Maps scatter today; a registry gathers them. But verify the wiring truly becomes testable before committing.

Top recommendation

Start with ① — relocate the Cloud Upload seam.

It's the highest-value of the five and it lands exactly where you're already working (test/cloud-coverage-100). cloud-upload.ts is the largest untested module in the tree, and it owns the genuinely tricky orchestration — leases, backoff, disconnect-mid-flight, alarm re-arm — that no pure reducer captures. The move is proven: makeDailyBudgetStore, makeAdmissionGate, and makeSavedStatusCoordinator already inject exactly these seams and are tested. You're applying a pattern the codebase has blessed, not inventing one.

Goal-driven loop (interface = test surface)
  1. 1. Characterise current behaviour through CloudUpload with the live ports → e2e green today
  2. 2. Inject { ledger, upload, alarms, badge, setSettings, authFlow } → same e2e stays green
  3. 3. Add unit tests driving drainUploadJobs via fakes → suite green, drain now covered
then ④ http.ts tests — smallest lift, likely the red-gate fix
then ② ③ apply the same seam-relocation to outbox & broadcaster
defer ⑤ only if ①–④ prove the pattern carries into the lifecycle
