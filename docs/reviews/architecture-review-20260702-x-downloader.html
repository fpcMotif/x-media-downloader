The good part — 5 strengths, and the lesson each teaches

Each verified against the live tree; the lesson is the transferable rule, not praise.

S1 · Option-returning DOM adapters at the irreversible-click boundary

confirmed

core/clear/clearer.ts (pageScope, tweetIdOfArticle, findArticle, findFeedbackButton → Option)

Why it’s good: depth at exactly the seam where Element | null conventions fail silently. “Absent” is a first-class, exhaustively-checked case — the compiler refuses a caller that forgets the none-branch — at the single highest-consequence bug class in the codebase (clicking the wrong destructive thing).

Lesson: when a module’s failure mode is “silently do the wrong destructive thing if a lookup was null and nobody checked,” return Option/Result instead of nullables. The type system becomes a reviewer for precisely the bug class that matters most.

S2 · Deterministic idempotency keys make Sync-Event replay safety a construction-time invariant

confirmed

core/sync/events.ts (syncEventId over deviceId × requestId × kind)

Why it’s good: “don’t double-record a re-sent batch” stops being an operational concern (dedup logic, upsert heuristics) and becomes a property of the id itself: same tuple → same eventId, so every at-least-once path (Outbox retry, backoff replay, offline flush) is idempotent at the consumer with zero coordination. Deleting it would re-scatter dedup heuristics across 3+ delivery boundaries.

Lesson: at any durable outbox / at-least-once boundary, derive record identity deterministically from content + context, never a fresh id per attempt — an entire class of “did this already land?” bugs collapses into one pure function.

S3 · CloudProvider registry: identity as one data record, behavior behind its own adapter seam

weakened → still real

core/cloud/provider.ts · consumed fork-free at 13 sites (cloud-upload.ts ×10, options cloud.tsx ×3) · RevokeRecipe + one interpreter

Why it’s good: every identity-data read — Settings field names, OAuth config, label, revoke recipe — is a lookup on one keyed record; delete PROVIDERS and 13 call sites regrow hand-written gdrive/dropbox forks. The discipline is the boundary: the record holds identity only; per-provider behavior (byte uploaders) stays behind its own adapter seam per ADR-0017. Even OAuth teardown is data: RevokeRecipe’s enum-tagged shape + one generic interpreter, instead of N quirky revoke functions.

Lesson: when N call sites fork on the same small enum, ask whether the fork is really per-variant data — if so, one keyed record kills all N conditionals. But keep per-variant behavior as adapters behind their own seam; stuffing closures into the record would turn a data table into a shallow grab-bag.

S4 · Optional-port-with-live-default injection, retrofitted onto shipped modules with zero caller edits

weakened → still real

background/cloud-upload.ts · sync-outbox.ts (13 optional ports) · siblings: capture-outbox, clear-coordinator

Why it’s good: production wiring stays trivially simple (background.ts passes only the required orchestrator deps), while a test overrides exactly the ports its scenario touches. Because the relocations kept the module interface byte-identical, commits 6ff69a5/7b5ef31 needed zero background.ts edits — proof the idiom retrofits without an interface-breaking rewrite. The sharp boundary rule: a port is optional exactly when its live binding is a global (storage item, browser API, clock); deps that close over caller state stay required.

Lesson: for side-effecting collaborators inside an orchestrator, make the port optional and default it to its live global binding — zero DI ceremony in production, precise per-path control in tests, retrofittable later without touching callers.

S5 · Claim-state ledger gives the irreversible Clear at-most-once-per-scope semantics by construction

weakened → still real

core/clear/ledger.ts (tryClaim: none|failed → clearing) · background/clear-coordinator.ts

Why it’s good: the pure reducer encodes the full claim lifecycle (cleared never re-claims; failed deliberately retryable), so any re-entry — duplicate settle tasks, partial multi-scope resolution, re-downloads — is at-most-once per (tweet, scope) by state construction, not ad-hoc guard flags. It composes with the serial queue rather than replacing it: the queue makes each read-modify-write atomic across awaits; the claim state dedupes logical duplicates that serialization alone would happily run twice.

Lesson: when an irreversible action can be re-attempted by re-entrant async paths, encode attempt→won/lost as explicit claim state in a pure ledger — and pair it with serialized RMW, because a claim transition is only atomic while the read-claim-write window stays synchronous.

Honorable mentions (verified, not counted): the coverage gate scoped to the testable layer with its rationale written beside the thresholds in vitest.config.ts — undermined only by point 19; and RevokeRecipe, folded into S3.

Top recommendation

Start with the 30-minute hygiene batch, then Candidate B. The hygiene batch (points 3, 19, 20) is pure deletion + one script edit — the isSyncConfigured import fixes a user-visible contradiction, and folding coverage + backend into check makes every subsequent change safer for zero design cost. Then Candidate B: it is the highest-leverage structural item because it fixes two verified findings at once (the trapped usePageAction/formatter logic and the wrong-seam source-text tests), uses an idiom this codebase has already landed five times (S4), and covers the newest never-browser-verified surface — the destructive popup actions. Candidate A is the cleanest classical deepening (a drifted two-adapter seam) and slots naturally after; C, D, E follow in any order.

goal loop (per candidate): 1) characterise at the target interface → green on today’s code
2) deepen behind that interface → same tests stay green · 3) delete superseded shallow tests (the source-text greps) → suite green

Method. 4-phase workflow, 49 agents: 6 readers (haiku/sonnet) → 9 dimension-scoped finders (sonnet) → 1 curator + 32 adversarial verifiers (Fable-tier), + 4 first-hand re-verifications by the synthesizer. One tooling-digest agent failed structured output and was excluded; its ground was independently covered by the config-tooling finder (points 19–20 carry first-hand re-verification).

Refuted in verification (1): “clear-scope toggle list drifted between popup and Worklist panel” — the popup’s omission of clearAllListsOnSave is specified in the 2026-07-01 design doc, not drift.

Not re-litigated: the 13 candidates refuted across the 2026-06-21/30 rounds (message-bus, handoff machine, boot() split, broad overlay decomposition, schema-by-consumer split, Drainer, …) and all 18 ADRs.
