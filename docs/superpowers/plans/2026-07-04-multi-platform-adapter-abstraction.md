## What changed

**Domain model** (`src/core/schema/index.ts`): `MediaItem.tweetId`→`postId`, `.handle`→`.author`, new required `platform: 'x'|'instagram'|'threads'` field (new `Platform` schema export). `src/core/sync/events.ts`'s `SyncMediaMeta` (the direct Convex `media` mirror) renamed identically + gained `platform`.

**Compiler-guided rename, not a hand-authored file list.** The schema change was made first, then `bun run typecheck` enumerated every real call site precisely — this is more reliable than grepping for `tweetId`/`handle`, since most textual hits (worklist/clear-ledger/capture/tab-broadcaster/saved-status/selection's `TweetGroup`) are **independent, deliberately-unrenamed** concepts that only happen to share the old field names:
- `core/clear/*`, `core/capture/*` (Knowledge Capture/TweetRecord), `TweetGroup.tweetId` (core/selection.ts) — untouched. Clear-on-save and text capture stay X-only by design (spec Non-goals); `TweetGroup` is its own independent grouping key.
- Wire-message field NAMES that reference a post by id (`ClearTweetRequest.tweetId`, `RefreshMediaUrlRequest`/`TabMessagingPort.tweetId`, `SweepEnqueueRequest`, `RecoverTweetMediaRequest`, `DownloadTraceEntry.tweetId`, sidecar JSON's `handle`/`tweetId` keys) **kept their old names** — only the VALUE assigned to them changed (`item.postId` instead of `item.tweetId`). This is the same "keep the wire shape, change the source" pattern as the filename-template aliases.
- Every genuine `MediaItem`/`SyncMediaMeta` field access DID change: `core/resolver/index.ts`, `core/adapters/x/{index,dom,detection-store}.ts`, `core/download/{admission,destination,filename,media-url-refresh}.ts`, `core/sync/events.ts`, `background/{admission-gate,cloud-upload}.ts` (call-site mapping only, cloud-upload.ts's own `UploadCandidate.handle` interface left alone), `entrypoints/background.ts`, `entrypoints/overlay.content/{handlers.ts,index.tsx}`, `entrypoints/popup/history-section.ts`. Plus every test fixture constructing/reading a `MediaItem`/`SyncMediaMeta` literal (19 test files).

**Filename template aliasing** (`core/download/filename.ts`): `{handle}`/`{tweetId}` are now permanent aliases for `{author}`/`{postId}`; `{platform}` is a new available placeholder. Default template and existing saved templates are unchanged.

**Adapter interface + registry** (new):
- `core/adapters/types.ts` — the `PlatformAdapter` interface.
- `core/adapters/x/tracked-response.ts` — `isGraphqlMediaUrl` relocated here from `entrypoints/inject/tee.ts` (which now just re-exports it), consolidating X's full detection surface into `core/adapters/x/`. Widened signature (`url, requestHeaders?`) per the design's Instagram/Threads header-matching need; X's implementation ignores the second param.
- `core/adapters/x/adapter.ts` — `xAdapter: PlatformAdapter`, a thin composition over the *unchanged* existing X functions (`index.ts`/`dom.ts`/`walk.ts`/`resolve.ts`/`syndication.ts`) — zero internal X-adapter logic moved or rewritten.
- `core/adapters/registry.ts` — `ALL_ADAPTERS`, `adapterForUrl` (URL-keyed, for `background.ts`'s multi-tab dispatch), `adapterForHostname` (hostname-keyed, for a content script's boot-time single-adapter selection).
- `core/adapters/meta-shared/media-node.ts` — the structural `image_versions2`/`video_versions`/`carousel_media` walker for the (not-yet-built) Instagram/Threads adapters to share, built and fully tested as a standalone module now per the spec.

**Convex backend** (`backend/convex/schema.ts`, `sync.ts`): additive, backward-compatible schema change — `media`/`media_state` gain optional `platform`/`postId`/`author` alongside the still-present optional `tweetId`/`handle` (both sides optional, per the existing `media_state.tweetId` precedent, so a schema push never breaks on old stored rows). New indexes `by_post`/`by_platform_post`. `materializeState` seeds both old and new columns on every write. New migration mutation `backfillPlatformFields` (mirrors the existing `backfillTweetId` migration) + verification query `platformBackfillRemaining` — **not yet run against a live deployment**; that's this migration's "deploy 1" landing in code, execution is a separate, user-initiated step. Deploy 2 (drop `tweetId`/`handle`, require the new columns) is explicitly future work, gated on `platformBackfillRemaining` returning 0.

## Instagram + Threads adapters (built)

**Status: BUILT, registered, uncommitted→committed this pass.** `src/core/adapters/instagram/adapter.ts` and `src/core/adapters/threads/adapter.ts` now implement `PlatformAdapter`, sharing detection logic through two new `meta-shared/` modules:

- `meta-shared/post-node.ts` — structural "find post-shaped objects anywhere in a JSON tree" walker, keyed on a node carrying both `code` (string) and `user.username` (string). Recurses into nested post-shaped nodes for free, which is how Threads' `reposted_post`/`quoted_post` resolve as independent `MediaItem`s with zero Threads-specific unwrapping code — the generic recursive walk finds them as their own post-shaped nodes.
- `meta-shared/detect.ts` — combines `post-node.ts` + the already-built `media-node.ts` into `detectMediaItems(json, platform)`, the full `detectFromResponse` pipeline both adapters call, parameterized only by the `platform` tag.

**Both adapters:**
- Instagram: `matchesUrl`/`hostMatch` = `www.instagram.com` only (no bare-domain redirect target, unlike X's two hosts). `isTrackedResponseUrl` matches `/graphql/query` OR `/api/v1/` (both surfaces Instagram's web client hits, per research), deliberately loose since detection is shape-driven, not URL-driven — a false-positive URL match only costs one wasted parse that returns `[]`. No repost/quote concept exists on Instagram (confirmed by research), so no unwrapping logic was needed there.
- Threads: `hostMatch` covers both `www.threads.net` and `www.threads.com` (April 2025 domain migration, same backend behind the redirect — one adapter, no per-domain branching). `isTrackedResponseUrl` matches `/api/graphql` (doc_id-dispatched persisted queries, no human-readable op name to filter on the way X's tee does), same "loose is safe" reasoning as Instagram. Repost (`reposted_post`) and quote-post (`quoted_post`) both resolve correctly under their own `postId`, proven by dedicated tests, not just asserted in comments.

**DOM-resolution decision (both adapters): tee-map-only, no independent DOM fallback.** `detectRenderedMedia` returns `[]` unconditionally; `resolveHoverItem`/`canResolveHoverItem` only ever look up the network-tee-populated `detected` map. This was a deliberate choice, not a shortcut two ways:
1. The design spec's own Open Questions flag both platforms' video hover/poster DOM idiom as unverified, needing live DevTools inspection.
2. Unlike X's `pbs.twimg.com`/`video.twimg.com` (a CDN URL scheme independently verified over years, letting X's DOM path do quality-upgradable resolution), no CDN URL scheme here has been live-verified. A guessed selector risks resolving to nothing, or to the wrong image, on click — worse than admitting the gap, because a guessed-but-wrong DOM resolver *looks* like real functionality while tee-map-only visibly fails closed until the network tee has actually seen the media.

Neither adapter implements `findMediaNeedingRecovery` — both platforms' oEmbed endpoints are Meta-app-registration-gated, so no public/no-auth recovery fallback exists (confirmed by research, matching the design spec's `PlatformAdapter` interface comment, not merely left unbuilt).

**Registry wiring:** `core/adapters/registry.ts`'s `ALL_ADAPTERS` now lists `[xAdapter, instagramAdapter, threadsAdapter]`; `registry.test.ts` gained coverage asserting `adapterForUrl`/`adapterForHostname` resolve `instagram.com`/`threads.net`/`threads.com` to the correct adapter and never to `xAdapter`, and that an X url/hostname never resolves to the new adapters.

**Everything here is research-informed (2024–2025 reverse-engineering write-ups), not live-verified** — no browser access exists in this environment to confirm against a real Instagram/Threads session. Structurally sound per research; needs live verification (network tab + DOM inspection) before anyone treats a specific endpoint match, header name, or DOM selector decision as confirmed working.

**Deliberately NOT done in this pass, and why:**
- `wxt.config.ts` host permissions and the two content-scripts' `matches` arrays (`inject.content.ts`, `overlay.content/index.tsx`) were **not** widened. Both content scripts currently import X's adapter functions directly and have zero registry-dispatch wiring — widening host permissions/matches now would inject a script on Instagram/Threads pages that does nothing useful (no DOM resolution wired up, the tee not connected to the registry), which is worse than not injecting at all.
- No clear-on-save equivalent, no Knowledge Capture extension, no Instagram Stories support — all explicitly out of scope per the design spec's Non-goals.

## Bug: "Download all" always fails on real Instagram media, despite correct detection (fixed, one manual step remains)

**Symptom.** On a real Instagram reel (`https://www.instagram.com/reels/DaMt25qvpHY/`), the overlay dock correctly showed "Download all detected media (4)" — detection was confirmed working via a Bun script running the actual shipped `detectMediaItems` against a faithful reconstruction of the real envelope. But clicking it always produced a `queued → failed` launcher transition within ~150–1200ms, with **zero console output anywhere** and **zero network requests to any `cdninstagram.com` media path** — meaning `handleDownload` never ran at all, one level before either of the two debug-logging fixes added while chasing this (commits `682dd47`, `39ff403`) could capture anything.

**Root cause (confirmed by full pipeline trace, not just inference).** `src/core/sender-guard.ts`'s `ALLOWED_CONTENT_SCRIPT_ORIGINS` hardcoded only `https://x.com`/`https://twitter.com`. The registry rewiring above widened `wxt.config.ts`'s `host_permissions` and both content scripts' `matches` to Instagram/Threads, but never touched this guard — an entirely separate allow-list that was never in this plan's scope to begin with (it predates the multi-platform work and lives in `src/core/`, not `src/entrypoints/`).

Exact mechanism: overlay → `sendTracked` → `browser.runtime.sendMessage({_tag:'DownloadRequest', ...})` → `background.ts`'s `onMessage` listener calls `isMessageAllowed('DownloadRequest', sender, ownId)` → `sender.tab` is set (content script) → `originOf(sender)` = `'https://www.instagram.com'` → **not in the allow-list** → returns `false` → listener returns `false` synchronously, `handleDownload` is never invoked → Chrome resolves the sender's `sendMessage()` promise with `reply: undefined` (no listener claimed the async channel) → `safeSend` classifies this as `{status:'ok', reply: undefined}` (not `'error'`, not `'context-invalidated'`) → back in `sendTracked`, `reportFailures(undefined)`/`reportSkipped(undefined)` both no-op (zero console output, exactly as observed) → `r?.completed !== undefined && r.completed === r.total` → `undefined !== undefined` → `false` → launcher → `--failed`. The ~150–1200ms-then-fast-reset timing also matches: this is a synchronous guard rejection, not a `queue.ts` `Schedule.exponential` retry chain (which would take seconds).

**Fix (3 files, TDD).**
1. `src/core/sender-guard.ts` — added `'https://www.instagram.com'`, `'https://www.threads.net'`, `'https://www.threads.com'` to `ALLOWED_CONTENT_SCRIPT_ORIGINS`, mirroring `wxt.config.ts`'s `host_permissions`/content-script `matches` list above. This is the actual fix.
2. `src/core/sender-guard.test.ts` — regression tests: allows a `DownloadRequest`-shaped tag from an Instagram content script, and from both Threads hosts.
3. `wxt.config.ts` — added `'https://*.cdninstagram.com/*'` to `optional_host_permissions` (same pattern as the existing `pbs.twimg.com`/`video.twimg.com` pair). This is a separate, secondary latent gap: it only matters once a user enables the size/daily-budget admission filters (`probeActive`) or Cloud Upload/`fetched` strategy for Instagram media — none of which gate the default-settings repro above — but is a genuine hole on the same host-list pattern, so fixed alongside. Threads' media CDN host is still unconfirmed/not added (no evidence found for it in this pass).

**Verification: all four green.** `bun run check` (98 files, 1188 tests), `bun run test:coverage` (100% statements/branches/functions/lines: 2301/2301, 1381/1381, 588/588, 1952/1952), `bun run build` (manifest confirmed to include the new `cdninstagram.com` optional host permission), backend `bun run test` (45 tests).

### What this means for Instagram/Threads today

With the tee (`inject.content.ts`) and the overlay (`overlay.content/index.tsx`) both now boot-dispatching via the registry, and `wxt.config.ts`/the manifest granting the hosts, the content scripts actually inject and run on Instagram/Threads pages for the first time. Concretely:
- The MAIN-world tee will capture and parse Instagram/Threads network responses (`detectMediaItems` via each adapter's `detectFromResponse`) into the overlay's `DetectionStore`, the same store X uses.
- Any Quick Grab / badge hover that resolves via the tee-populated map (`resolveHoverItem`/`canResolveHoverItem` — both `detected.get(key) ?? null` / `detected.has(key)` for IG/Threads, per the adapters' by-design tee-map-only posture) will work.
- `detectRenderedMedia` returns `[]` for both new platforms by design, so the DOM-only rescan paths (`onRescanClick`, `scanRenderedMedia`'s initial paint, `handleRefreshMediaUrl`'s DOM fallback) contribute nothing extra there — this degrades gracefully to "nothing found yet," never a crash or wrong result, and was confirmed by reading every call site, not merely inferred from the adapter's own doc comments.
- The launcher/dock, Download-all, and the download queue/admission/cloud-upload/Convex-sync pipeline downstream are all platform-agnostic already (from the earlier schema-generalization pass) and need no further changes to work once a `MediaItem` reaches them, regardless of its `platform`.
- Every X-only feature enumerated above (clear-on-save, worklist, sensitive-content reveal, syndication recovery, Knowledge Capture) is wired to X-specific DOM/functions that simply don't match anything on an Instagram/Threads page — they don't error, they just find no matching articles/controls and no-op, exactly as before this task on any non-X page the extension was never injected into at all.

## X-only feature leak found via LIVE browser testing, fixed (gate every setup point)

**Status: BUILT.** `bun run check` green (98 test files, 1185 tests, 100% coverage over `src/core`+`src/lib`), `bun run build` green.

**Found by live testing, not static review — this is exactly why the live-verification step in this plan's own caveats mattered.** The previous section's content-script rewiring was reviewed by reading the diff, `tsgo --noEmit`, and `bun run build` — all of which passed, because none of them can catch "this code runs on a platform it was never supposed to run on when the platform still executes without error." Loading the rebuilt extension in Chrome Canary against a real, logged-in instagram.com session (not a stub/mock) surfaced a real console line the static review missed entirely:

```
[XMD] capture harvest path=/api/graphql source=timeline all=true → got 0 record(s)
```

Knowledge Capture (`harvestTweets`, Non-goals: X-only forever) was firing its full tree-walk on every tracked Instagram GraphQL response. It happened to return 0 records only because Instagram's JSON doesn't structurally coincide with `harvestTweets`' tweet-node shape today — that's luck, not a guarantee, and the wasted parse + log noise was a real scope violation regardless of the record count.

**Root cause.** Before the `matches` array widened from X-only to X+Instagram+Threads, every X-only feature in this file — clear-on-save/worklist, Knowledge Capture, sensitive-content auto-reveal, syndication recovery, and the cross-device "Saved ✓" status sweep — was *implicitly* platform-scoped for free: the content script simply never ran anywhere but X. Widening `matches` to inject the same script on three platforms silently deleted that implicit scoping. The prior task's own instructions correctly said these features "must stay wired directly to their X-specific functions, unconditional" (i.e. don't route them through the `PlatformAdapter` interface) — but that language didn't also require re-adding the platform gate the old single-platform `matches` array used to provide as a side effect. `harvestFrom` was gated deep inside its own body in one place but its call site at the `xmd:media-response` listener was not gated, which is exactly the "easy to miss one call site" failure mode coarse gating is meant to avoid.

**Fix: gate every X-only feature's SETUP point, not each call site.** In `src/entrypoints/overlay.content/index.tsx`, wrapped each feature's setup/registration in `if (adapter.platform === 'x') { … }` (the `adapter` closure variable resolved once at boot, per "Boot-time adapter selection") so the machinery never initializes at all on Instagram/Threads tabs — no wasted `MutationObserver`, no wasted computation, not merely "gated deep inside a call so it happens to return early":

- `recoverMissingVideos` (syndication video-recovery) — early-returns before its `store.needsRecovery(document)` DOM walk when `adapter.platform !== 'x'`.
- The cross-device "Saved ✓" sweep's `MutationObserver` construction — only constructed when `adapter.platform === 'x'`; never built at all on Instagram/Threads (this feature is treated as X-only per this file's own instructions, even though it wasn't named in the design spec's Non-goals list — its `SavedIndex`/Convex queries and `TWEET_ARTICLE_SEL`/`tweetIdOfArticle` DOM selectors are X-DOM-specific).
- `applySettings`'s `setAutoReveal(...)` call (sensitive-content auto-reveal) — gated; its `MutationObserver` is never created off-X.
- `applySettings`'s `setStubCollapse(...)` call ("Not interested" feedback-stub collapse) — gated alongside auto-reveal.
- `applySettings`'s `scheduleSavedSweep()` call — gated so the debounce timer for the Saved-status sweep is never even armed off-X (redundant with, but not the same code path as, the `MutationObserver` gate above — the timer could otherwise still fire once from other triggers without the observer).
- `harvestFrom(json, detail.path)` at the `xmd:media-response` listener — the actual reported bug. The call site itself is now gated (`if (adapter.platform === 'x') harvestFrom(...)`), not just `harvestFrom`'s internal `captureEnabled` check.

**Explicitly NOT gated, and why that's correct:** the media-detection pipeline (`adapter.detectFromResponse`, `adapter.detectRenderedMedia`, `adapter.resolveHoverItem`, `adapter.canResolveHoverItem`) and the Quick Grab/badge/launcher hand-off machinery stay unconditional — they're already platform-generic via the `PlatformAdapter` interface and are meant to run on all three platforms. `clearScope`/`clearNotInterested`/`forYouClearExpect` and the `handlers.ts` clear-on-save family (`handleClearVisible`, `handleClearWholeList`, `handleDrainPage`, `handleSweepPage`, `handleClearTweet`) were left as plain functions with no added gate: they are message-triggered only (fired by a popup button click, and the popup is out of this task's scope), never self-initializing at content-script boot, so there is no "setup point" to coarsely gate — off X they already fail closed by finding zero matching `TWEET_ARTICLE_SEL` articles, exactly as documented in the previous section's "What this means for Instagram/Threads today."

**Zero X behavior change.** Every edit is a wrapper (`if (adapter.platform === 'x') { existing-code }` or an early-return guard) around code that is untouched inside the conditional — nothing X does today changed. Confirmed by re-running the exact same verification suite as the prior pass and confirming identical counts (98 test files / 1185 tests / 100% coverage / clean build) — no test needed to change to accommodate this fix, which is itself evidence the change is additive-only.

**`src/entrypoints/overlay.content/handlers.ts` — reviewed, unchanged.** Its two `deps.adapter.*` call sites (`handleRefreshMediaUrl`, `handleClearDetectedMedia`) already dispatch generically and needed no gate. Its X-only clear-on-save handlers have no eager setup/registration to gate (see above) — confirmed by reading every handler in the file, not merely assumed.

**Caveat, unchanged from the prior section:** this fix was still verified by reading + typecheck + build + the existing test suite, not by a new automated test — `overlay.content/index.tsx` remains at 0% automated coverage (entrypoints are excluded from the coverage gate by design). The *discovery* of the bug this section fixes came from live Chrome Canary testing precisely because that gap exists; the fix itself was not re-verified live in this pass (no second round of Chrome Canary testing was performed after applying the gates) — that is the natural next step before calling this fully closed.

## Photo DOM-hover for Instagram/Threads (built); video stays tee-map-only

**Status: BUILT.** `bun run check` green (99 test files, 1217 tests, oxfmt/oxlint/tsgo clean), `bun run test:coverage` 100% statements/branches/functions/lines (2349/2349, 1423/1423, 598/598, 1991/1991) over `src/core`+`src/lib`, `bun run build` green, backend `bun run test` green (45 tests).

This closes the gap the prior section's own caveats flagged: Instagram/Threads previously resolved a hover **only** through the tee-populated map (`detected.get(key)`), with `resolveHoverItem`/`canResolveHoverItem` falling straight to `null`/`false` for anything the network tee hadn't already seen — so hovering a photo before its GraphQL/REST response landed (or on a post the tee missed entirely) showed no badge and Quick Grab did nothing, even though the rendered `<img>` was sitting right there in the DOM with a real, directly-fetchable CDN url. This pass adds a genuine DOM fallback for photos, mirroring X's own `resolveImageElement`/`isGrabbablePhotoUrl`/`mediaKeyFromUrl` shape, while explicitly leaving video untouched.

### Live-verification facts this relied on (Chrome Canary, real logged-in Instagram + Threads, this session)

1. **Photos have a real, direct CDN url in the rendered DOM.** A `<img>` inside an Instagram/Threads post has `currentSrc`/`src` pointing straight at `scontent-{region}.cdninstagram.com` (Instagram, e.g. `scontent-lga3-2.cdninstagram.com`) or the bare `scontent.cdninstagram.com` (Threads) — not a `blob:`/placeholder. Both are the same CDN family the tee-detected `image_versions2.candidates[].url` already points at.
2. **Content vs. avatar is distinguished by a path-family suffix, not the whole prefix.** Every cdninstagram media url carries a `t{N}.{N}-{N}` path segment (e.g. `t51.82787-15`, `t51.71878-15`, `t51.2885-19`). The numeric prefix (`82787`, `71878`, `2885`) varies; the trailing `-15` vs `-19` is the actual load-bearing signal — `-15` is real post content (photo/video), `-19` is a profile picture/avatar. An unrelated `media4.giphy.com` embedded-GIF url was also observed on Threads (an external embed, not Instagram/Threads' own CDN) — excluded by the host check alone, since it isn't `*.cdninstagram.com`.
3. **Both region-prefixed and bare host forms must match.** `scontent-lga3-2.cdninstagram.com` (Instagram) and `scontent.cdninstagram.com` (Threads, no region prefix) are both real; a host check needs the whole `*.cdninstagram.com` family, not one exact hostname.
4. **Video has no DOM-derivable identity and no reasonable fallback.** A rendered `<video>` on a real Instagram reel uses a `blob:https://www.instagram.com/<uuid>` MediaSource src with `poster` empty/null; checking 8 ancestor levels up found zero nearby poster `<img>` (X's own `_video_thumb` fallback pattern has no Instagram equivalent). Threads' own video/poster DOM shape was **not** independently re-verified this session (only Instagram's reel was checked) — Threads defaults to the same tee-map-only posture as a reasoned default, not an independently confirmed fact.

### The key-normalization problem (fact #1 in the task brief) — investigated, resolved as "assume same-basename, flagged unverified," not silently swept under the rug

X's DOM path never needs cross-rendition normalization at the basename level: `upgradePhotoUrl` forces a canonical `name=orig` **query parameter** on any twimg url, while the path basename itself is rendition-independent by construction on that CDN. Instagram/Threads have no observed equivalent query-param scheme, so the open question was whether a rendered `<img>`'s srcset-selected (possibly smaller) rendition shares its path basename with the tee's own largest-`image_versions2`-candidate pick for the *same* asset.

**Investigated, not resolved with certainty.** No two renditions of the literal same asset were captured side-by-side this session to settle it definitively. `meta-shared/dom.ts`'s `mediaKeyFromMetaUrl` therefore ships with the straightforward "path basename minus extension, minus query string" key — the same shape as X's `mediaKeyFromUrl` — and its doc comment states plainly, in block-capitals, that this is an **unverified assumption, not a settled fact**, including the specific failure mode if it's wrong (DOM-hover on a smaller rendition either silently fails to resolve, or `resolveHoverItem`'s placeholder fallback mints a second, distinct `MediaItem` for the same asset the tee already has under a different key) and the fix direction if a future session confirms the assumption false (key off the numeric ID prefix shared across renditions, rather than the full basename). This is the honest state of the crux question — investigated, structurally reasoned about, but not proven with a live side-by-side capture.

### What was built

- **`src/core/adapters/meta-shared/dom.ts`** (new) — the Instagram/Threads counterpart to `x/dom.ts`: `isCdninstagramHost` (both host forms), `pathFamily`/`isContentPathFamily` (the `-15`/`-19` signal), `isGrabbableMetaPhotoUrl` (host + content-family gate), `mediaKeyFromMetaUrl` (gated key extractor, mirrors X's combined `xAdapter.mediaKeyFromUrl` shape rather than X's raw two-function split), `extFromMetaImgUrl`.
- **`src/core/adapters/types.ts`** — `PlatformAdapter` gained one new required method, `mediaKeyFromUrl(url): string | null` — the single dispatch point `overlay.content/index.tsx`'s `previewKeyFromMedia` now calls instead of hardcoding X's `mediaKeyFromUrl`/`isGrabbableMediaPreviewUrl`. Purely additive to the interface; every existing adapter had to (and does) implement it.
- **`src/core/adapters/x/adapter.ts`** — `mediaKeyFromUrl` implemented as `(url) => isGrabbableMediaPreviewUrl(url) ? mediaKeyFromUrl(url) : null`, i.e. X's own two historically-separate `dom.ts` exports combined into the one self-gated call the interface expects. Neither underlying `dom.ts` function was touched.
- **`src/core/adapters/instagram/adapter.ts`** / **`threads/adapter.ts`** — `mediaKeyFromUrl: mediaKeyFromMetaUrl`; `resolveHoverItem`/`canResolveHoverItem` gained a real DOM fallback (`resolveMetaImageElement`, gated on `HTMLImageElement` and `isGrabbableMetaPhotoUrl`) for when the tee map hasn't resolved the key yet — tee item still always wins when present (richer provenance: real `postId`/`author`), matching X's own `resolveHoverItem` precedence. `detectRenderedMedia` stays `() => []` for both — no post-identity (pk/code/author) is DOM-derivable without an anchor-walk this session didn't build/verify, so a rescan still contributes nothing extra; only single-item hover/Quick-Grab got a fallback, not the wholesale rendered-media rescan.

- **`src/entrypoints/overlay.content/handlers.ts`** — no changes needed this pass. Its one hover-key call site (`badgeInput`'s `deps.previewKeyFromMedia(badgeMedia) === badge.key`) already received `previewKeyFromMedia` as an injected function via `HandlerDeps` from the prior registry-rewiring pass, so it picks up the new adapter-dispatched implementation automatically with zero edits here.

### Videos: confirmed infeasible, deliberately not attempted

Per fact #4 above, no DOM-derivable video key exists for Instagram (and, by reasoned default rather than independent verification, Threads). `detectRenderedMedia` returning `[]` and the DOM fallback being gated on `element instanceof HTMLImageElement` together mean a hovered `<video>` on Instagram/Threads still resolves *only* through the tee map, exactly as before this pass — this was a deliberate scope boundary, not an oversight: attempting a guessed selector risks resolving to nothing or to the wrong asset on click, which is worse than the current fail-closed behavior.

### Zero X behavior change — verified, not just claimed

`xAdapter.mediaKeyFromUrl` is `isGrabbableMediaPreviewUrl(url) ? mediaKeyFromUrl(url) : null` — the exact same two-function gate the overlay's old inline `previewKeyFromMedia` ran (`media && isGrabbableMediaPreviewUrl(src) ? mediaKeyFromUrl(src) : null`), just relocated behind the adapter dispatch and with the `media &&` null-check turned into an early `if (!media) return null`. Confirmed by diffing the pre-change function against the new one line-by-line, not just by re-running tests. The full verification suite (`bun run check`/`test:coverage`/`build`, backend `test`) reports the same green status as every prior pass in this document, with `x/adapter.test.ts` gaining a dedicated `mediaKeyFromUrl` conformance test asserting the exact same grabbable/avatar/non-twimg/malformed cases X already handled.

### Honest caveats — do not oversell

- **NOT browser-verified end-to-end.** This build was not live-clicked or hover-tested in an actual browser with the extension rebuilt and reloaded in this pass. No consumer groups by `postId` on this hot path today, so this has no observed downstream effect, but it is a known, accepted gap, not a hidden one.
