Finding the Data: The Hands-On Hunt

Lesson 1 assumed you already had a blob of JSON in hand. This one is the step before that: given an unfamiliar site (or a familiar one that just broke), how do you actually find where its data lives — in under five minutes, without reading a single line of its source code?

Ask this one question first

Everything branches from: is the data on the page already, or does it show up after you do something?

Already there on load

A profile page, a single post permalink, the first screen of a feed — data the server had time to prepare before sending HTML.

→ Check the embedded script tag first. Fastest path, zero waiting.

Shows up later

Infinite scroll loading more posts, a modal opening, search-as-you-type, "load more" clicks.

→ Go straight to the Network tab and trigger the action while watching.

Path A: the embedded blob

Open the Console and run:

[...document.querySelectorAll('script[type="application/json"]')]
  .map(s => s.textContent.length)

That gives you every candidate and its size — the real content is usually the biggest one, or the one whose text contains a word you recognize from the page (a username, a caption fragment). Check with:

[...document.querySelectorAll('script[type="application/json"]')]
  .find(s => s.textContent.includes('SOMETHING_YOU_SEE_ON_SCREEN'))

Path B: the network tab

Following Chrome DevTools: Network panel and the walkthrough in How to Scrape Hidden APIs (this lesson's primary source):

  1. Open DevTools → Network tab, click the Fetch/XHR filter (cuts out images, CSS, fonts — everything that isn't a data call).
  2. Trigger the action — scroll, click, type — while the panel is open and recording.
  3. New rows appear. Click one, open the Preview tab (not Response) — it renders the JSON as an expandable tree, much faster to scan than raw text.
  4. Not sure which request has what you want, out of several? Use the panel's own Cmd/Ctrl+F to search across every captured response at once for a field name or value you recognize.
One thing worth a glance, not a deep dive Once you've found the request, the Headers tab shows what the request needed to succeed — usually just your ordinary session cookie, sometimes an extra app-identifying header the page's own JavaScript already attaches for you. For a passive reader (watching traffic your own logged-in session already generates), you don't need to reconstruct any of this by hand — you're not sending the request, you're reading the one the page sent anyway.

Either path, same next move

Once you have ONE real captured example — from the embedded blob or the network tab, doesn't matter which — you're back to Lesson 1: find the 2-3 fields that make something recognizably "the thing you want," and write the shape-signature walk. The hunt in this lesson is how you get the example to build that signature from; it is not itself the parser.
