Lesson 1 · Reverse-engineering social media SPAs

The Key Trick: Shape, Not Path

This session, you watched me pull real post data out of Instagram and Threads without ever being told where in the response it lived. Here's the one idea that made that possible — and why it'll outlive the next redesign of whatever platform breaks next.

The problem: paths are not stable

When I actually looked at a captured Instagram response, the post data was buried here:

root.require[0][3][0].__bbox.require[0][3][1].__bbox
    .result.data.xdt_api__v1__feed__timeline__connection
    .edges[0].node.media

That's not a typo-prone edge case — it's normal for a modern app built on Relay/GraphQL. The wrapper around your data (which query ran, how the client library bundles its cache, which surface served the response) changes constantly. If detection code says response.data.items[0].media, it breaks the moment that wrapper shifts even slightly — and it will shift, because none of it is a promise the site made to you.

The trick: check the shape, not the address

Instead of asking "where does the post live," ask: "what does a post look like, wherever it is?" A node in that pile of JSON is a post if it has a non-empty code string (the URL shortcode) and a user.username string sitting on it. Nothing else about its position matters.

Hardcoded path

const post =
  json.data.items[0]
    .media

Breaks the instant the wrapper changes shape — even if the post data itself is untouched.

Shape signature

function isPost(n) {
  return typeof n?.code
      === 'string'
    && typeof n?.user
      ?.username
      === 'string'
}

Survives the wrapper changing, because it never looks at the wrapper at all.

Then you walk every node in the tree — arrays, objects, all the way down — and test each one against that shape. When one matches, you've found a post, no matter how deep or how the wrapper is arranged this week:

function forEachPost(json, visit) {
  const walk = (node) => {
    if (Array.isArray(node)) { node.forEach(walk); return }
    if (typeof node !== 'object' || node === null) return
    if (isPost(node)) visit(node)
    for (const key of Object.keys(node)) walk(node[key])
  }
  walk(json)
}
Why this signature specifically code and user.username aren't decoration — the site's OWN page needs them to render a working permalink and byline. If Instagram removed them, their own UI would break too. That's the test for a good signature: would the site itself visibly break without this field? If yes, it's a safe thing to depend on.

Where the JSON tree comes from in the first place

Two sources, and you don't need to pick just one:

  • Watch the network. DevTools → Network → filter to Fetch/XHR. See Chrome DevTools: Network panel (the primary source for this lesson) for the exact clicks.
  • Read what's already on the page. Many sites embed the first batch of data directly in the HTML, in a <script type="application/json"> tag, so the page doesn't have to show a loading spinner while it re-fetches what the server already knew. This is called hydration — see the Apollo Client SSR docs for the general pattern (Instagram/Threads use their own internal version of the same idea, not Apollo specifically, but the shape of the trick is identical). You can find it with one line: document.querySelectorAll('script[type="application/json"]'), then check each one's text for a field name you're hunting for.
